# 로봇 원격 관제 및 모터 전류 상태 진단 시스템 (완료)

> **무엇을** — 소형 4WD 로봇을 원격 관제하고, 모터 전류로 구동부 이상을 진단하는 엣지-서버 분리 시스템
> **무슨 기술로** — Arduino(펌웨어) · C# WinForms/Python(관제·분석) · TCP/IP socket · C++/MFC 포팅
> **어떤 성능으로** — 전류 기반 3-클래스 진단 **정확도 99.3%**, 이물질 **재현율 100%**
> (약 8분 실측 3세트 / 세트 단위 3-fold 교차검증 **99.6%**, 과적합 폭 0.1%p)

**✅ 프로젝트 1 완료.** 유선 통신 → 무선 전환 → 안전로직 → 상태 진단 → TCP/IP 원격 관제 → **C++/MFC 포팅**까지 완료했습니다.

## 프로젝트 개요

반도체·제조 장비 SW의 관제 구조를 소형 로봇으로 구현한 학습·포트폴리오 프로젝트입니다.
"AI 없이도 완벽히 동작하는 시스템"을 먼저 구축하고, 그 위에 상태 진단과 원격 관제를 얹은 뒤,
같은 관제 시스템을 **C++/MFC로 다시 구현(포팅)** 하여 마무리했습니다.

| 구분 | 내용 |
|---|---|
| **엣지 (로봇)** | Arduino Uno + 4WD 스마트카 · 초음파/전류 센서 · 서보 · HC-06 블루투스 |
| **서버 (PC)** | C# WinForms 관제 GUI · Python 데이터 분석 · **C++/MFC 관제 (포팅)** |
| **통신** | 커스텀 바이너리 패킷 프로토콜 (XOR 체크섬) · 블루투스 · TCP/IP socket |
| **안전** | 하트비트 워치독 (통신 두절 시 자율 정지) |
| **상태 진단** | 모터 전류 시간영역 통계 기반 이상 감지 → 유형 분류 → 자동 대응 |
| **원격 관제** | TCP/IP socket 기반 브릿지 구조 · 양방향 · 멀티스레드 |

## 시스템 구조

```
[WinForms 관제]  ← GUI · 실시간 그래프 · 상태 진단 · 자동대응
      ↓  TCP/IP socket (네트워크)
[브릿지]         ← 하트비트 유지 · 명령/센서 양방향 중계
      ↓  시리얼 / 블루투스
[로봇]           ← 전류 측정 · 워치독 · 서보 경고
```

관제(원격 PC)와 로봇을 브릿지가 잇는 중앙관제 구조. 통신 계층(시리얼↔socket)을
교체해도 패킷 프로토콜을 그대로 재사용하도록 계층을 분리 설계했습니다.
이 계층 분리 설계 덕분에, 이후 관제 클라이언트를 **C# → C++/MFC로 교체**할 때도
동일한 패킷 프로토콜을 그대로 재사용할 수 있었습니다.

## 주요 기능

### 실시간 관제
- PC에서 로봇 방향 제어 (전/후/좌/우/정지, 비상정지)
- 초음파 거리 · 모터 전류 실시간 수신 및 그래프 표시 (GDI+ 직접 렌더링)
- 수신 스레드 분리 + UI 스레드 마샬링(Invoke)으로 안정적 실시간 갱신
- 공유 자원 동기화 — 송신 직렬화, 판정 상태 보호, 버퍼 소유 스레드 고정 (아래 참조)

#### 멀티스레드 공유 자원 정리

수신 스레드와 UI 스레드가 같은 자원을 만지는 지점을 점검해 세 가지를 수정했습니다.

| 자원 | 문제 | 조치 |
|---|---|---|
| `NetworkStream.Write` | 방향 명령(UI 스레드)과 서보 경고(수신 스레드)가 **동시 송신** 가능 → 패킷이 섞여 명령 유실 | `sendLock`으로 송신 직렬화 |
| 그래프 버퍼 `Queue<int>` | `Enqueue`는 UI 스레드, `ToArray()`는 수신 스레드에서 호출 → `Queue<T>`는 스레드 안전하지 않아 간헐적 예외 | 버퍼는 **UI 스레드 전용**으로 고정, 최근값은 별도 필드로 전달 |
| 판정 상태 (윈도우·경고 플래그) | 두 스레드가 함께 갱신 | `stateLock`으로 보호. **락 안에서는 상태만 계산하고 `Invoke`·송신은 락 밖에서** 수행해 UI 스레드와의 교착을 회피 |

> 비상정지 명령이 다른 패킷과 섞여 유실될 수 있는 구조였다는 점에서, 이 중 첫 번째는
> 안전 기능에 직접 영향을 주는 문제였습니다.

### 커스텀 패킷 프로토콜
```
[STX=0x02] [LEN] [CMD] [DATA...] [CHK] [ETX=0x03]
```
- CMD 대역 분리: `0x1_` 명령 / `0x2_` 센서 / `0x3_` 제어 / `0x4_` 진단 대응
- XOR 체크섬으로 데이터 손상 탐지
- 조각나서 도착하는 데이터를 상태 기반 조립기로 재조립
- **전송 계층 독립** — 시리얼과 TCP/IP socket 양쪽에서 동일 프로토콜 재사용

### 워치독 안전로직
- 100ms마다 하트비트 전송, 로봇이 미수신 시 **스스로 정지** (자율 안전장치)
- 원격 관제 시에는 브릿지가 하트비트를 담당하여 연결 유지

### 상태 진단 (감지 → 분류 → 대응)
- ACS712 전류센서 통합, 드리프트 대응 동적 영점 보정
- Python으로 정상/부하/이물질 데이터 분석 → 유형별 고유 특징 규명

  | 상태 | 평균 (`current_diff`) | 표준편차 |
  |---|---|---|
  | 정상 | 8.57 | 1.49 |
  | 부하(무게) | 10.18 | 1.59 |
  | 이물질(마찰) | 14.36 | 2.32 |

  > 약 8분 분량 실측 데이터(각 상태 3세트) 합산 기준. `current_diff` = 주행 구간의 모터 전류
  > 변화량 지표로, ACS712 → ADC 경로에서 산출되며 절대 물리 단위(mA) 환산 없이 **상대 지표**로
  > 사용합니다. 이물질(2.32) > 정상(1.49) 순으로 마찰이 클수록 변동이 커지는 설계 의도와 일치합니다.
  >
  > **데이터 정제:** 초기엔 정상 표준편차가 이물질보다 커서 물리적으로 이상했는데, 원본을 추적하니
  > **주행 종료 후 전류가 0으로 떨어졌음에도 로깅이 마지막 명령(FORWARD)을 유지한 채 계속 기록한
  > '꼬리 0 블록'** 이 원인이었습니다. 이 구간을 제거하는 전처리를 넣어 통계를 바로잡았고,
  > 이후 측정에서도 같은 로깅 현상이 재현됨을 확인했습니다.

- **이상 감지:** 슬라이딩 윈도우(W=20, 겹침) 평균 기반 실시간 판단 (직진 FORWARD 구간 한정)
- **유형 분류:** 윈도우 평균을 두 경계값(9.4 / 12.0)으로 정상 · 부하 · 이물질 3분류
- **구간 단위 윈도우:** 하나의 윈도우가 서로 다른 주행을 섞지 않도록, 구동 구간별로 분리해 생성
- **자동 대응:** 부하는 경고 표시, 이물질 지속 시 자동 정지 + 서보 좌우 경고

> **표준편차 조건을 제거한 이유 (설계 변경 기록)**
> 초기 구현에는 "변동이 크면 이물질"이라는 표준편차 조건(`std >= 2.8`)이 있었습니다.
> 데이터를 정제·확대한 뒤 재검증하니 **정상 1.49 대 부하 1.59로 표준편차가 1.07배 차이에 불과해
> 두 상태를 가르는 데 쓸 수 없었고**, 이물질은 평균만으로 이미 재현율 100%였습니다.
> 오히려 변동이 큰 부하 구간이 이물질로 오분류되어 불필요한 자동 정지를 유발했습니다.
> 조건을 제거한 결과 **부하 재현율이 83.6% → 97.7%로, 전체 오분류가 260건 → 68건(74% 감소)** 했습니다.
> 초기 가설을 데이터로 기각하고 판정 규칙을 단순화한 사례입니다.

> **정상 오탐의 진짜 원인 — 모터 기동 돌입전류 (설계 변경 기록 2)**
> 남은 오탐의 원인을 추적하다 윈도우 생성 방식 자체에 문제가 있다는 것을 발견했습니다.
> 한 CSV에는 FORWARD 구간이 여러 번 나타나는데(주행→정지→주행), 이전 구현은 이 구간들을
> **하나로 이어붙인 뒤** 윈도우를 만들어서, 윈도우가 구간 경계를 넘나들며 앞 주행의 끝과
> 다음 주행의 시작을 섞고 있었습니다.
>
> 문제는 구간 시작마다 **모터 기동 돌입전류**가 나타난다는 점입니다. 정지한 DC 모터는
> 역기전력(E=k·ω)이 0이라 기동 순간 전류가 V/R까지 치솟고, 회전이 붙으면서 정상값으로
> 내려옵니다. 실측에서도 구간 시작값이 본체 평균의 **최대 2.58배**까지 튀고 곧바로 감쇠했습니다.
> 전체 데이터에서 구간 경계가 59개, 경계를 넘나드는 윈도우가 **1,121개**였습니다.
>
> 구간을 분리해 윈도우를 만들자 **정상 오탐률이 2.43% → 0.41%(83% 감소)**, 정확도가
> **98.5% → 99.3%** 로 올랐습니다. 그동안 "원인 모를 순간 스파이크"로 설명하던 현상이
> 물리적으로 설명되는 기동 과도 현상이었음을 데이터로 확인한 것입니다.
>
> "하나의 윈도우가 서로 다른 주행을 섞으면 안 된다"는 것은 데이터를 보기 전에도 참인
> 명제이므로, 성능 튜닝이 아니라 **원칙적인 수정**으로 판단해 채택했습니다.

#### 진단 성능 (실측 검증 + 반복 개선)

약 8분 분량 실측 CSV(정상/부하/이물질 각 3세트, FORWARD 구간, 꼬리 0 블록 제거)에
판정 로직을 적용해 **재현한** 결과입니다. 판정은 `current_diff`의 **슬라이딩 윈도우(W=20, 겹침)
평균**을 경계값으로 분류합니다. 전체 재현 코드는 [`analysis/classify.py`](analysis/classify.py) 참조.

**검증 스크립트와 실제 관제 앱의 판정 규칙을 일치시켰습니다.**
분석 스크립트는 98.5%를 냈지만 실제 앱(`Form1.cs`)은 다른 규칙(경계 9.5, `std >= 2.8` 포함)으로
동작하고 있어, README가 주장하는 성능을 제품이 내지 못하는 상태였습니다. 판정 로직을
`Classify()` 순수 함수로 분리하고 양쪽 규칙을 일치시켰으며, 두 파일에 상호 참조 주석을 달아
한쪽만 수정하면 어긋난다는 것을 알 수 있게 했습니다.

**구간 단위 윈도우도 실제 앱에 반영했습니다.**
분석 코드만 고치면 같은 불일치가 재발하므로, `Form1.cs`도 **명령이 바뀌면 윈도우 버퍼를
비우고 주행 구간에서만 값을 누적**하도록 수정했습니다. 이 과정에서 기존 앱의 결함도
발견했는데, 정지 구간에서도 버퍼에 값을 먼저 넣은 뒤 반환하고 있어 **전류 0이 윈도우에
섞이고 있었습니다.** 주행을 재개하면 윈도우 평균이 낮게 계산되어 이상이 있어도
정상으로 판정될 수 있는, 안전 기능이 침묵하는 방향의 결함이었습니다.

또한 진단 대상을 **직진(FORWARD) 구간으로 한정**했습니다. 경계값이 FORWARD 실측
데이터만으로 도출됐기 때문이며, 후진 구간은 해당 데이터를 측정한 뒤 확장할 예정입니다.

**판정 방식을 데이터 규모에 따라 재검증했습니다.**
초기 2분 데이터에선 정상 오탐의 원인이 **순간 전류 스파이크**(예: `0 → 16 → 21`)임을 발견해
스파이크에 강건한 중앙값으로 판정했습니다. (배터리 방전 가설도 세웠으나 데이터로 기각.)
이후 데이터를 **약 8분(3세트, 4배)으로 확대해 재검증**하니, 스파이크 영향이 희석되고
부하-정상 경계 구분이 더 중요해져 **평균 + 경계값 9.4**가 최적이었습니다(당시 98.5%).
데이터 규모에 따라 최적 하이퍼파라미터가 달라진다는 것을 관찰하고, 충분한 데이터로 재결정했습니다.
이후 아래 교차검증에서도 3개 fold 모두 `mean`을 선택해 이 결정이 재확인됐습니다.

**혼동 행렬** (구간 단위 윈도우 평균, LOW=9.4 / HIGH=12.0, 행: 실제 / 열: 예측, 단위: 윈도우 개수)

| 실제 \ 예측 | 정상 | 부하 | 이물질 | 합계 |
|---|---|---|---|---|
| **정상** | **973** | 4 | 0 | 977 |
| **부하** | 20 | **1087** | 0 | 1107 |
| **이물질** | 0 | 0 | **1292** | 1292 |

- **전체 정확도 99.3%** — 3,376개 윈도우 중 3,352개 정답 (**Macro-F1 99.2%**)
- **이물질 재현율 100%** — 가장 위험한 이물질을 단 한 번도 놓치지 않음 (1,292/1,292)
- **정상 오탐률 0.4%** (4/977) · **부하 놓침 1.8%** (20/1,107)
- 전체 오류 24건이 모두 정상↔부하 사이이며, **이물질 관련 오류는 0건**

| 클래스 | 정밀도 | 재현율 | F1 |
|---|---|---|---|
| 정상 | 97.99% | 99.59% | 98.78% |
| 부하 | 99.63% | 98.19% | 98.91% |
| 이물질 | 100% | 100% | **100%** |

### 성능 개선 경과

| 단계 | 정확도 | 정상 오탐 | 비고 |
|---|---|---|---|
| 초기 (앱에 `std >= 2.8` 조건) | 94.3% | — | 검증 스크립트와 규칙 불일치 |
| ① std 조건 제거 · 규칙 일치화 | 98.5% | 2.43% | 오분류 260건 → 68건 |
| ② **구간 단위 윈도우** | **99.3%** | **0.41%** | 기동 돌입전류 오염 제거 |

> ①과 ②는 윈도우 모집단이 달라(4,555 → 3,376) 정확도를 직접 비교할 수 없으므로,
> ②의 효과는 **같은 파라미터에서의 정상 오탐률**로 비교했습니다 (2.43% → 0.41%, 83% 감소).

> **경계값 결정 방법:** 경계값 × 판정방식(평균/중앙값) 조합을 **전수 탐색**해 정확도가 최대인
> 조합을 선택했습니다. 경계를 올리면 정상 오탐은 줄지만 이상을 놓치는 비율이 늘고, 내리면
> 반대가 되는데, 두 오류가 33건 대 35건으로 균형을 이루는 9.4가 최적이었습니다.
> HIGH=12.0은 **부하 최대 11.35와 이물질 최소 13.20 사이가 실제로 비어 있어** 그 중간을 잡은
> 값이며, 이물질 재현율 100%가 우연이 아닌 이유입니다.
> 사후에 통계로 검증하면 9.4는 정상 평균에서 2.49σ, 12.0은 이물질 평균에서 4.55σ 지점입니다.

### 일반화 성능 — 세트 단위 교차검증

경계값을 전체 데이터로 탐색한 뒤 같은 데이터로 평가하면 낙관적으로 편향됩니다.
이를 확인하기 위해 **Leave-One-Set-Out 3-fold 교차검증**을 수행했습니다.
재현 코드는 [`analysis/classify_cv.py`](analysis/classify_cv.py) 참조.

> **왜 세트 단위로 나누는가:** W=20 슬라이딩 윈도우는 이웃 윈도우와 19개 샘플을 공유합니다.
> 윈도우를 랜덤으로 섞어 분할하면 거의 동일한 윈도우가 train과 test 양쪽에 들어가
> **데이터 누수(leakage)** 가 발생해 테스트 점수가 부풀려집니다. 그래서 측정 세트(파일)
> 단위로 분할했습니다.

| 지표 | 값 |
|---|---|
| in-sample (전체로 탐색 후 전체 평가) | 99.67% |
| **교차검증 평균** | **99.57%** (fold별 표준편차 0.28%p) |
| **과적합 폭** | **+0.10%p** |
| 배포 파라미터 고정 평가 | 99.30% |
| fold별 선택 방식 | 3개 fold 모두 `mean` (경계값 변동폭 0.05) |

**과적합은 0.1%p로 사실상 없습니다.** 파라미터가 경계값 2개뿐이고 클래스 분리가 뚜렷하기
때문이며, 3개 fold 모두 동일한 판정 방식을 선택해 하이퍼파라미터 선택도 안정적이었습니다.

> **성능 수치의 한계 (명시)**
> - **윈도우가 겹치므로 3,376개는 독립 표본이 아닙니다.** 겹침을 보정한 유효 독립 표본은
>   약 169개이며, 그 기준 95% 신뢰구간은 **99.6% ± 1.0%p** 입니다.
> - 단일 로봇·단일 노면·단일 배터리 조건에서 측정했으므로 **환경 일반화는 검증되지 않았습니다.**
> - 부하 강도가 1단계뿐이라 경계값의 견고성은 추가 검증이 필요합니다.

## C++/MFC 포팅

취업 목표(반도체 장비 제어·AGV SW 개발)의 요구 기술인 **C++ / MFC** 역량을 확보하기 위해,
이미 C#으로 완성한 관제 시스템을 C++/MFC로 다시 구현했습니다.
같은 시스템을 두 언어로 구현함으로써 **언어에 종속되지 않는 설계 이해**를 보여주는 것이 목표입니다.

단계적 검증 원칙에 따라 콘솔 → 소켓 → GUI 순서로 진행했습니다.

| 단계 | 내용 | 결과물 |
|---|---|---|
| **1. 콘솔** | 커스텀 패킷 프로토콜(빌드·파싱·XOR 체크섬)을 C++로 이식 | `cpp/PacketTest` |
| **2. Winsock** | TCP 서버/클라이언트로 실제 패킷 송수신 (에코 통신) | `cpp/EchoServer`, `cpp/EchoClient` |
| **3. MFC GUI** | 대화상자 기반 관제 — 버튼 클릭 → 패킷 전송 → 에코 수신·로그 | `cpp/MfcControl` |

- **패킷 프로토콜 재사용:** C#에서 설계한 `[STX][LEN][CMD][DATA][CHK][ETX]` 구조를
  C++로 포팅. `Packet.h`/`Packet.cpp`로 분리하여 콘솔·서버·GUI 세 프로젝트에서 공통 사용
- **Winsock 소켓 통신:** C#의 `System.Net.Sockets`에 대응하는 Winsock2 API로
  초기화·연결·송수신·정리 전 과정 직접 구현
- **MFC 대화상자 관제:** 방향 제어 버튼(전/후/좌/우/정지) → CMD 패킷 전송,
  연결/해제 및 상태 표시, 수신 로그 출력. C# WinForms 관제의 핵심 조작 화면을 재현

## 설계 원칙

1. **역할 분리** — 로봇은 실행, PC는 판단·진단
2. **유선 우선, 무선/네트워크는 나중** — 검증된 토대 위에 확장
3. **단계적 검증** — 한 방향씩 검증하여 문제 원인 격리
4. **계층 분리** — 애플리케이션 프로토콜을 전송 수단과 독립 설계 (시리얼↔socket, C#↔C++ 재사용)
5. **데이터 기반 의사결정** — 임계값 등을 실측 분석으로 도출
6. **재현 가능성** — 문서에 적힌 성능 수치는 저장소의 코드로 그대로 재현됨
